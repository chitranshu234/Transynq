1. Executive Summary & Problem Scope

Transynq is a high-availability digital twin monitoring platform built for critical electrical substation infrastructure (Heavy Step-Down Power Transformers, Medium Distribution Transformers, and 11 kV Switchgear Panels). Electrical assets in transmission and distribution networks are subject to severe dielectric, thermal, and mechanical stresses. Transynq continuously digests simulated multi-sensor telemetry, computes quantitative asset health scores according to international engineering standards (IEEE C57.104, IEC 60076-7), fires state-transition alerts, and provides operators with historical telemetry audit capabilities.

Core Mandatory Outcomes Satisfied

  • Live View of Asset Health: Continuous telemetry of Top Oil Temperature, Hot-Spot Winding Temperature, Electrical Load Factor, and Dissolved Hydrogen ($H_2$) gas generated from simulated physical equations.
  • Automated Anomaly Alerting: Deterministic transition-based alerting that flags Warning and Critical states without flooding database logs on every tick.
  • Historical Audit Logs: Time-filtered history queries (15 min, 1 hr, 24 hr) accompanied by dual-axis visual trends and exportable tabular logs.

3. Mathematical Formulation & Health Logic

A. Thermal Inertia Drift Equations

Under the NORMAL scenario, temperatures follow ambient damping toward nominal setpoints with physical inertia: 

Oil_Temp(t+1) = Oil_Temp(t) + (60.0 - Oil_Temp(t)) * 0.12 + Random(-0.3, +0.3)
Winding_Temp(t+1) = Oil_Temp(t+1) + 12.0 + Random(-0.6, +0.6)
Load_Factor(t+1) = Load_Factor(t) + (68.0 - Load_Factor(t)) * 0.10 + Random(-0.75, +0.75)
H2_Ppm(t+1) = H2_Ppm(t) + (30.0 - H2_Ppm(t)) * 0.12 + Random(-0.9, +0.9)

Under the OVERHEATING scenario, thermal runaway is simulated by positive incremental steps: 

Oil_Step = 1.0 + Random(0.0, 1.5) → (+1.0 to +2.5 °C / tick)
Oil_Temp(t+1) = min(102.0, Oil_Temp(t) + Oil_Step)
Winding_Gradient = 13.0 + Random(0.0, 3.0) → (+13 to +16 °C hot-spot rise)
Winding_Temp(t+1) = min(118.0, Oil_Temp(t+1) + Winding_Gradient)

B. Health Evaluation Thresholds (IEEE C57.104 / IEC 60076-7)

Parameter Nominal Range Warning Threshold Critical Breach Standard Reference
Top Oil Temperature ≤ 75.0 °C > 75.0 °C > 85.0 °C IEC 60076-7 Thermal Loading Guide
Hot-Spot Winding Temp ≤ 88.0 °C > 88.0 °C > 98.0 °C IEEE C57.91 Insulation Degradation
Load Factor ≤ 85.0 % > 85.0 % > 95.0 % Rated Substation Nameplate Limit
Dissolved Hydrogen ($H_2$) ≤ 100.0 ppm > 100.0 ppm > 200.0 ppm IEEE C57.104 DGA Interpretation

Health Score Formula:

Health_Score = max(0, min(100, 100 - (10 * Count(WARNING)) - (25 * Count(CRITICAL))))

4. Ground Rules & Interview Walkthrough

A. AI Usage Disclosure (Ground Rules Requirement)

  • Which parts AI produced: AI assisted with scaffolding repetitive boilerplate (Spring Boot JPA entities, repository interfaces, DTOs) and translating Tailwind styling structures.
  • How code was verified: Verified via automated unit tests (mvn test — 5/5 passing), scripted PowerShell end-to-end API audits, raw SSE stream inspections, and OWASP security header validation.
  • Where AI was overruled: AI initially proposed an overly complex distributed architecture using Apache Kafka, bi-directional WebSockets, and OAuth2 microservices. I overruled this because transformer telemetry is unidirectional (sensor to cloud), and adding external brokers introduces needless operational failure points. Instead, I mandated Server-Sent Events (SSE) with Spring SseEmitter, reducing external latency to zero and delivering native browser auto-reconnects. Furthermore, I overruled random jump simulation in favor of bounded thermal inertia equations.

B. The Decision Changed (Interview Walkthrough)

  • JPA Relationship FetchType (LAZY vs EAGER): Originally, Reading.asset and Alert.asset were declared with FetchType.LAZY. When serializing readings over asynchronous SSE threads outside the original database transaction, this triggered LazyInitializationException. I evaluated wrapping controller methods with @Transactional(readOnly = true) versus switching to FetchType.EAGER. I chose FetchType.EAGER because Asset is a small reference entity with only 6 scalar fields, completely eliminating lazy-loading failures and N+1 query overhead while ensuring thread-safe serialization across background SSE emitters.

C. Transition-Based Alerting

  • Instead of firing database alert rows every 3 seconds during a fault (which would flood the database with thousands of duplicate rows per hour), the alert engine triggers only on state changes (HEALTHY → WARNING → CRITICAL) and sets a resolvedAt timestamp when conditions return to normal.
